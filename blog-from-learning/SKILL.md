# Blog from Learning

帮助用户把亲自遇到、尝试和理解的事情写成长期成长记录。文章的价值来自真实问题、证据和认知变化，而不是题目看起来多么宏大。

## 从真实材料开始

先利用当前环境中实际可访问、与任务有关的材料，例如：

- 用户提供的代码、项目文件、笔记和学习记录
- Git history、diff、提交信息和相关 issue
- 报错、日志、失败尝试、修复过程和 Debug 线索
- 实验设计、运行结果、对照数据和未验证的猜想
- 对话中用户自己提出的问题、解释和认知变化

从最相关、成本最低的材料开始，已有证据足够时停止。不要声称读过不可访问的材料，也不要为了形成完整故事而补造经历、动机、项目背景、实验步骤或结果。

如果用户只想选题或梳理素材，默认保持只读；只有用户明确要求写入文件、修改博客或提交改动时才修改内容。

## 选择值得写的问题

优先寻找具有个人证据和认知变化的题目：

- 真正踩过、且根因有启发性的坑
- 一个终于想明白的问题或被修正的 mental model
- 一次结果有意思或反直觉的实验
- 项目中有真实约束与权衡的技术决策
- 从不会到会的过程，尤其是关键转折点
- 两个概念之间意外但可解释的联系
- 值得分享、并实际尝试过的学习方法实验

一个好题目通常能用具体问题表达，而不是仅用技术名词命名。优先写窄而深、证据充足的切面。默认避开“XXX 从入门到精通”“XXX 全面教程”等泛化选题；用户明确要求教程时也应清楚区分亲历内容、通用知识与外部资料。

如果同时发现多个候选题，按真实材料的强度、认知变化的清晰度、问题的具体程度、对他人的迁移价值，以及能否用代码或实验支撑来排序。不要为了给出选项而凑数。

## 写作前形成文章主张

在动笔前，从材料中明确：

1. **核心问题**：文章真正试图回答的一个问题。
2. **真实经历**：发生了什么，用户当时如何理解、尝试和修正。
3. **可用证据**：哪些真实代码、提交、日志、实验或笔记能支撑叙述。
4. **关键认识**：最有价值、最不显然的理解是什么，以及它的适用边界。
5. **读者收益**：读者读完后能更好地理解、判断、调试或行动什么。

区分可观察事实、用户的解释和仍待验证的推断。材料之间有冲突时保留冲突并指出需要验证之处，不要替用户消除不确定性。

若这些信息尚不足以支撑文章，先明确列出已知材料与最关键的缺口。优先请求最小必要补充，例如相关代码、原始错误、一次实验结果或当时的错误理解；不要用通用知识填补个人经历。即使信息不足，也可以在用户需要时提供选题方向、采访式问题或标有空缺的提纲，但不能把空缺写成事实。

## 组织文章

让结构服从这次经历的因果与认识变化，不强制统一模板。常见叙事可以是：

> 问题 → 探索 → 错误理解 → 实验或代码 → 真正理解 → 总结

只有实际经历包含这些环节时才使用。也可以围绕一次 Debug 时间线、一个技术决策的权衡、实验的假设与结果，或两个概念的连接来组织。

开头尽快落到具体情境和问题。代码、日志和实验只保留能推动理解的部分，并解释它们证明了什么、没有证明什么。结尾提炼可迁移的认识、适用条件和仍未解决的问题，不要重复全文或强行升华。

## 保持个人而准确的声音

写成一个认真学习 CS 的学生记录自己真正理解问题的过程：清楚、技术准确、有个人思考、有真实过程、不故作高深。

- 保留有意义的犹豫、误判、失败尝试和转折，不把过程改写成事后全知。
- 使用具体语言说明“我原来怎么想”“什么证据让我改变理解”“现在如何判断”。只有材料支持时才用第一人称陈述。
- 解释必要的机制、因果与边界，少堆术语、口号、空洞过渡和 AI 套话。
- 不把偶然观察泛化成普遍规律；不确定处明确标注。
- 不伪造引用、数据、benchmark、时间线或可复现性。需要补充外部事实时优先查证一手资料，并让外部资料服务于用户的真实故事，而不是淹没它。
- 保持用户原有表达习惯；修改现有草稿时保留其中真实、有辨识度的声音。

## 交付方式

根据请求交付最小但完整的结果：

- **发现选题**：给出少量候选，每个说明真实素材、核心问题、独特认识、读者收益和尚缺证据。
- **写作准备**：给出文章主张、素材清单、事实与推断边界，以及顺着故事生成的提纲。
- **撰写文章**：输出完整草稿，并对任何待用户确认或补充之处作醒目标记。
- **修改文章**：优先增强真实细节、因果链、技术准确性和个人声音；不要仅做表面润色或把文章改成统一的 AI 风格。

最终检查：每个个人经历是否有材料依据；每个技术结论是否被证据支撑或清楚限定；文章是否围绕一个值得回答的问题；删掉个人过程后若仍像任意作者都能写出的泛化教程，应继续收窄题目或补充真实材料。
